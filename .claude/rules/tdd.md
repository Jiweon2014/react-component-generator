# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.**
> 단계를 건너뛰거나, 순서를 바꾸거나, 일부만 적용하지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙을 우선**한다.
- 이 파일은 프로젝트별 규칙이 없을 때 쓰는 **기본값(fallback)** 이다.
- 두 규칙이 충돌하면 프로젝트 규칙을 따르고, 충돌하지 않는 부분은 이 파일을 따른다.

## 적용 기준

### TDD를 반드시 적용하는 대상

- 비즈니스 로직
- API (엔드포인트, 요청/응답 처리, 에러 매핑)
- 유틸 함수
- **버그 수정** (버그를 재현하는 실패 테스트를 먼저 작성한다)

### TDD가 불필요한 대상

- 타입 정의
- 설정 파일
- 순수 UI (로직 없는 마크업, 스타일)
- SQL

판단이 애매하면 **적용 대상으로 본다.**

## RED-GREEN-REFACTOR 사이클

### RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- 테스트를 **반드시 실행해서 실패를 확인**한다. 실행하지 않은 테스트는 RED가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 오타, import 오류, 설정 오류로 실패한 것은 RED가 아니므로 테스트부터 고친다.

### GREEN: 최소한의 코드로 통과

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI.** 지금 테스트가 요구하지 않는 기능, 분기, 옵션은 추가하지 않는다.
- **신규 테스트와 기존 테스트가 모두 통과**하는지 실행해서 확인한다.

### REFACTOR: 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- 모든 테스트가 **green을 유지**하는지 변경 후 실행해서 확인한다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 다음 RED에서 시작한다.

### 반복

REFACTOR가 끝나면 **다음 동작에 대한 RED로 돌아간다.** 모든 동작이 끝날 때까지 반복한다.

## 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성했다면 **그 코드를 삭제하고 RED부터 다시 시작**한다.
- "참고용"으로 남기거나, 주석 처리하거나, 보면서 다시 쓰는 것도 **금지**한다. 삭제는 삭제다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드도 깨진다. 테스트는 작성하는 데 1분도 걸리지 않는다. 단순하다면 더더욱 비용이 없다. |
| "나중에 추가하겠다" | 나중에 쓴 테스트는 이미 통과하는 코드에 맞춰 작성되어 **실패를 한 번도 증명하지 못한다.** 그 테스트는 아무것도 검증하지 않는다. |
| "시간이 없다" | 테스트 없는 코드는 디버깅과 회귀 수정으로 더 많은 시간을 쓰게 한다. 급할수록 사이클을 지킨다. |
| "삭제하면 낭비" | 이미 쓴 코드는 매몰 비용이다. 테스트 없이 남기면 검증되지 않은 코드를 떠안는다. 삭제하고 테스트부터 다시 쓰는 편이 싸다. |
| "프로토타입이다" | 프로토타입은 종종 그대로 제품이 된다. 적용 대상이면 프로토타입도 예외가 아니다. |
