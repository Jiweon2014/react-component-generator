# commit

작업 트리의 변경사항을 분석해 컨벤션에 맞는 한국어 커밋으로 남긴다.
커밋은 이력에 남는 작업이므로, 메시지와 묶음을 사용자에게 먼저 보여주고 승인받은 뒤에만 실행한다.

## 절차

### 1. 변경사항 분석

아래 명령으로 현재 상태를 파악한다.

```bash
git status --short
git diff            # unstaged
git diff --staged   # staged
git log --oneline -10   # 기존 메시지 스타일 참고
```

- git 저장소가 아니면(`git status`가 실패하면) 커밋을 진행하지 말고 사용자에게 알린다.
- 변경이 없으면 그 사실만 알리고 끝낸다.
- untracked 파일은 `git diff`에 나오지 않으므로 `git status`로 확인하고 필요하면 내용을 읽는다.
- `.env`, 키·토큰·비밀번호가 담긴 파일 등 커밋하면 안 될 것으로 보이는 파일이 있으면 제외하고 사용자에게 알린다.

### 2. 논리적 단위로 분류

하나의 커밋은 하나의 목적만 담는다. 나중에 이력을 읽거나 되돌릴 때 단위가 섞여 있으면 곤란하기 때문이다.

- 서로 다른 목적(기능 추가 + 버그 수정 + 설정 변경 등)이 섞여 있으면 여러 커밋으로 나눈다.
- 같은 목적에 속한 파일(컴포넌트 + 해당 테스트 + 스타일)은 한 커밋으로 묶는다.
- 한 파일 안에 서로 다른 목적의 변경이 섞여 있으면 사용자에게 어떻게 나눌지 묻는다.
- 변경이 작고 목적이 하나면 커밋 하나로 충분하다. 억지로 쪼개지 않는다.

### 3. 커밋 메시지 작성

형식:

```
<type>: <요약>

<본문 (선택)>
```

| type | 용도 |
|------|------|
| feat | 새로운 기능 추가 |
| fix | 버그 수정 |
| refactor | 동작 변화 없는 구조 개선 |
| chore | 빌드·설정·의존성·문서 등 기타 작업 |

- 요약과 본문은 한국어로 쓴다.
- 요약은 한 줄, 가능하면 50자 안팎으로 "무엇을 했는지"를 적는다. 끝에 마침표는 붙이지 않는다.
- 본문은 요약만으로 "왜"가 전달되지 않을 때만 쓴다. 비워도 된다.
- 위 4가지 type으로 분류하기 애매하면 임의로 다른 type을 만들지 말고, 가장 가까운 것을 제안하면서 사용자에게 확인한다.

예시:

```
feat: 버튼 컴포넌트에 로딩 상태 추가
fix: 폼 제출 시 중복 요청이 발생하는 문제 수정
refactor: useFetch 훅의 에러 처리 로직 분리
chore: eslint 설정 업데이트
```

### 4. 커밋 실행

사용자가 커밋을 요청한 것 자체가 실행 허가이므로, 별도의 승인을 기다리지 않고 바로 커밋한다.
커밋별로 `git add <파일들>` → `git commit`을 실행한다.
`git add .`나 `git add -A`는 의도하지 않은 파일이 섞일 수 있으므로 쓰지 않고, 커밋 단위에 속한 파일을 이름으로 지정해서 추가한다.

커밋 후에는 `git log --oneline -n <커밋 수>`로 결과를 확인하고, 커밋별 파일 목록과 메시지를 사용자에게 보고한다.
잘못 묶였거나 메시지를 고치고 싶을 수 있으므로, 사용자가 수정을 요청하면 그때 `--amend` 등으로 반영한다.

## 하지 않는 것

- push는 요청받지 않았으므로 하지 않는다.
- `--amend`, `--no-verify`, 강제 옵션은 사용자가 명시적으로 요청하지 않는 한 쓰지 않는다. pre-commit 훅이 실패하면 원인을 알리고 해결 방법을 묻는다.
